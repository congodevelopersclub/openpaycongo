# Provider deposits

`RecordProviderDeposit` is an application seam, not an HTTP or mobile-authentication contract. A future authenticated installation flow must authorize the organization and source installation before it constructs a `ProviderTransfer`.

The action stores only keyed digests for private customer and installation lookup, encrypts sender and receiver identifiers (and provider references) at rest through Laravel encrypted casts, and hides those fields from model serialization. It records a provider credit and its two balanced ledger entries in one transaction. A repeated provider reference returns `replayed` only when its complete keyed JSON payload digest matches; otherwise it returns `conflict` without writing another entry. Reversals append a separate immutable deposit and balancing entries. Persisted deposits and ledger entries reject Eloquent updates and deletes; direct database-administrator or query-builder mutation is an operational authority boundary, not a supported application behavior.

The schema targets PostgreSQL, SQLite, MySQL, and MariaDB through Laravel's portable UUID, foreign-key, unique-index, timestamp, and unsigned-big-integer migrations. The automated slice proves SQLite behavior. Its unique provider-reference and reversal constraints plus transactional retry/re-read path are the concurrency safety mechanism, but live PostgreSQL/MySQL/MariaDB contention tests remain acceptance work for a database-service matrix. No balance column is maintained.

`DEPOSIT_LOOKUP_TOKEN_KEY` is mandatory dedicated token material (at least 32 characters), not an `APP_KEY` fallback. The current `v1` seam does not yet provide a multi-key lookup ring; **issue #165 remains open** until a versioned key-ring migration and live database contention matrix are delivered. Do not rotate the configured deposit lookup-token key before that follow-up exists. The conservative supported-currency allowlist is currently `CDF`; expanding it needs an explicit product and accounting decision.
