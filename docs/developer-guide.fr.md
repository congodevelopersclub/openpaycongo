# Guide du développeur

Ce guide décrit le prototype OpenPay Congo tel qu’il est implémenté dans ce dépôt. Le parcours produit est : SMS → Android → Laravel → rapprochement limité à l’organisation → portefeuille client → webhook HTTP sortant signé. Il ne s’agit pas d’un flux websocket. Le dépôt reste explicitement impropre à la production : utilisez des organisations de test, des identifiants jetables et des SMS synthétiques ; ne faites jamais transiter de vrais fonds ni de vraies données client.

## Cloner, vérifier et construire

L’environnement de vérification pris en charge utilise Docker. Depuis la racine du dépôt, lancez les contrôles locaux complets des composants concernés :

```bash
bash scripts/ci/fast-feedback.sh local laravel
bash scripts/ci/fast-feedback.sh local flutter
```

Pour créer un APK de débogage, utilisez la cible d’artefact CI existante. Elle exécute l’analyse et les tests Flutter, les tests Android natifs et le test cryptographique natif, puis exporte l’APK signé pour le débogage :

```bash
bash scripts/ci/fast-feedback.sh pr flutter
test -s android-client/build/ci/app-debug.apk
```

L'importation d'un parseur SMS échoue en mode fermé si l'APK n'a pas été construit avec `OPENPAY_OPERATOR_PATTERN_SIGNING_PUBLIC_KEY`. Fournissez la clé publique de l'autorité de parseur déjà configurée avant de lancer la cible d'artefact. Le serveur utilise la configuration protégée `OPENPAY_OPERATOR_SMS_PATTERN_SIGNING_SECRET` correspondante. Cette autorité de parseur est distincte de la signature d'appairage QR ; ne créez pas de nouvelle autorité pour ce parcours. GitHub CI utilise une clé synthétique de test pour son APK. Cet APK ne vérifie que des versions synthétiques correspondantes dans un environnement jetable et ne doit jamais servir avec un déploiement ou des données réels. Sans épingle publique de parseur, l'importation est refusée.

Installez cet artefact sur un émulateur isolé ou un appareil de test :

```bash
adb install -r android-client/build/ci/app-debug.apk
adb shell monkey -p com.congodeveloperclub.opencongopay 1
```

Cet APK sert uniquement à une démonstration contrôlée du prototype. Il n’est pas destiné à la distribution Play ni à une mise en production. La configuration Gradle Android `release` utilise une signature de débogage. L’application demande l’autorisation Android `RECEIVE_SMS` dans son contexte et protège les écrans qui utilisent les SMS tant que cette autorisation n’est pas accordée. Utilisez un profil d’émulateur ou d’appareil séparé, avec des données de test jetables.

Pour lancer Laravel hors CI, suivez [operations.md](operations.md) afin de configurer Compose, les migrations, les clés, TLS et les variables d'environnement protégées. Ne copiez pas de valeurs de production dans `.env`, l'historique du shell, les commandes d'exemple, les artefacts de compilation ou le dépôt. L'appairage continue d'utiliser l'URL HTTPS canonique, la graine de signature d'appairage et le mode de confiance déjà configurés. Les versions de modèles SMS utilisent l'autorité de signature de parseur déjà provisionnée et son épingle publique correspondante dans l'APK ; cette autorité est distincte de la clé d'appairage. Ne créez pas de remplacement et n'utilisez pas la signature d'appairage pour les versions de parseur.

## Parcours produit et limites de confiance

1. **Appairer et activer.** Un administrateur vérifié démarre le parcours existant par QR et code SAS pour son organisation. L’application mobile vérifie les données d’appairage signées, confirme le code d’authentification court, récupère l’enveloppe d’activation opaque et effectue l’accusé de réception chiffré avant d’activer les opérations mobiles normales. Le QR est une donnée d’amorçage confidentielle et à usage unique. Suivez [ADR 004](adr-004-secure-device-enrollment.md) ; ne faites pas de capture d’écran et ne journalisez ni ne réutilisez ces données.
2. **Capturer localement.** Android exige `RECEIVE_SMS`. Son `SmsDeliverReceiver` exporté reçoit la diffusion système `SMS_RECEIVED`, tandis que les règles natives ne conservent que les messages dont l'expéditeur normalisé correspond exactement à un expéditeur de confiance approuvé par un administrateur. Android écrit chaque message capturé dans son journal local chiffré avant de l'analyser. Le corps brut du SMS reste sur le téléphone. Après l'analyse, l'expéditeur normalisé, l'identifiant de recherche client et les champs de transaction circulent uniquement dans l'enveloppe authentifiée et chiffrée ; ni le corps brut ni le contenu analysé ne sont transmis à l'analytique. Le serveur stocke les preuves du parseur chiffrées au repos.
3. **Approuver une version du parseur.** Un opérateur financier vérifié ouvre **SMS payment patterns** et propose un modèle littéral synthétique avec l'identifiant fournisseur, l'expéditeur SMS exact et les cinq champs requis. La proposition reste `pending_review` et ne change pas l'analyse mobile. Un opérateur vérifié par MFA l'approuve, puis crée une version mobile signée avec une expiration future en UTC. La page exporte le JSON canonique pour le téléphone appairé. L'appairage conserve sa propre limite de confiance. Les versions de parseur utilisent l'autorité d'opérateur préconfigurée, distincte ; un import ne peut pas choisir une nouvelle clé de signature et un APK sans l'épingle publique du parseur refuse l'importation. Voir [la limite d'intégration des modèles opérateur](operator-pattern-integration.md) pour le format signé et les limites de compatibilité.
4. **Importer, analyser et préparer.** Dans la boîte de réception, ouvrez **SMS deposit sync**, choisissez **Import signed parser**, collez le JSON canonique `encoded_release` copié et choisissez **Verify and install**. Avant de recevoir le SMS fournisseur, utilisez **Review rules** pour enregistrer son expéditeur exact. L'importation ne modifie pas les règles d'expéditeur. Lorsque l'application est déverrouillée, appairée et autorisée à lire les SMS, un scanner littéral borné applique le modèle installé. Il exige exactement une occurrence de chacun des champs `{amount}`, `{currency}`, `{reference}`, `{customer}` et `{occurred_at}`. Il accepte les montants CDF en unités principales et les convertit en unités mineures entières. Les identifiants du fournisseur et les dates sont validés avant la préparation. Les versions inconnues, expirées, antérieures, mal formées ou dont l'empreinte ne correspond pas sont refusées ; les messages sans version utilisable restent à examiner. Un message analysé et préparé pendant la période de validité signée peut être renvoyé après l'expiration de cette version, car le serveur compare cette période à l'heure de réception capturée du SMS. Un message brut resté non analysé après l'expiration exige une nouvelle version approuvée et une nouvelle analyse ; son heure capturée doit aussi appartenir à la période de validité signée de cette nouvelle version.
5. **Envoyer les données analysées.** L'application crée l'opération `sms_deposit` pour le protocole v1 existant sur `POST /mobile/envelopes`. Android la chiffre avec la clé directionnelle d'appairage et un compteur durable ; la requête contient l'identifiant d'installation, le compteur, le nonce et le texte chiffré, sans jeton bearer. La charge utile interne contient les champs du dépôt et des preuves de parseur bornées (`kind: signed_release`, `provider`, `sms_sender`, `parser_version`, `sms_received_at`, `evidence_digest` et `parser_release_id`). Elle ne contient pas le texte du SMS. Chaque tentative réseau utilise un nouveau compteur durable et l'idempotence du serveur empêche les doublons de crédit. Le serveur lie chaque enveloppe à l'installation appairée et à son compteur ; le texte chiffré d'un ancien appairage ne peut donc pas être rejoué sous un nouvel appairage. Après avoir authentifié la réponse chiffrée `recorded` ou `replayed`, l'application marque les mêmes preuves de dépôt capturées comme acquittées dans son journal chiffré. Elle conserve ces preuves sans supprimer ni modifier les champs du dépôt.

   `POST /mobile/deposits` est une route de compatibilité distincte, authentifiée par le jeton bearer mobile de l’installation appairée. Elle accepte l’ancienne charge utile de transfert et ne prouve pas à elle seule l’analyse d’un SMS signé. Ne l’utilisez pas pour contourner `sms_deposit` dans le parcours d’acceptation SMS. Le contrat d’enveloppe et la limite de compatibilité sont décrits dans [mobile-envelope-v1.md](mobile-envelope-v1.md).

6. **Valider et créditer.** Laravel authentifie et déchiffre l'enveloppe avant de lire la commande interne. Pour `sms_deposit`, le serveur retrouve le condensat du transcript dans l'organisation de l'installation appairée et vérifie la version approuvée, le fournisseur, l'expéditeur, la version et la période de capture ; l'heure de réception ne peut pas dépasser l'heure actuelle de plus de cinq minutes. Le `release_id` UUID de la liste des versions est opaque et différent du condensat `parser_release_id` enregistré dans les preuves du dépôt. L'organisation et l'installation source proviennent de l'installation appairée, jamais de la charge utile. Un transfert identique répété est reconnu comme déjà enregistré ; des données différentes sous la même référence fournisseur limitée à l'organisation sont refusées. Un enregistrement réussi ajoute des écritures équilibrées et immuables au grand livre, ainsi qu'une écriture de crédit client. Les preuves du parseur sont chiffrées en base par le modèle du dépôt et exclues de sa sérialisation. La signature approuve les règles du parseur ; l'enveloppe authentifie la possession de la clé du téléphone appairé. Ces contrôles ne prouvent pas indépendamment que le téléphone a exécuté ces règles ni qu'un opérateur téléphonique ou un fournisseur de paiement a envoyé le SMS. Un téléphone appairé compromis peut fabriquer un signalement ; le crédit reste donc provisoire et `unverified`.
7. **Rapprocher comme administrateur.** Un opérateur financier limité à son organisation, avec MFA vérifiée, peut consulter le rapport de rapprochement masqué. La liste, la consultation et la correction d’un dépôt exigent que l’organisation de l’opérateur corresponde à celle du dépôt. La page propose un flux de correction motivé et audité ; le parcours de crédit SMS réussi n’exige ni annulation ni réparation. Le rapprochement vérifie la cohérence interne du grand livre, pas le règlement du fournisseur.
8. **Lire le portefeuille client.** Un opérateur financier émet une application OAuth client credentials avec le périmètre `wallets:read` et accorde explicitement à cette application l'accès à un client de la même organisation. Le consommateur obtient un jeton bearer auprès de `/oauth/token`, puis lit `/services/customers/{customer}/wallet`. La réponse comprend le solde CDF `available_minor` et `settlement_status: unverified` ; elle exclut les identifiants de recherche et les références fournisseur. `available_minor` est un solde comptable interne, pas un blocage ferme ni une preuve que les fonds peuvent être dépensés ou réglés. La révocation de l'autorisation supprime l'accès au portefeuille ; la révocation des identifiants de l'application invalide l'accès de ses jetons. Le périmètre et l'autorisation explicite par client sont deux contrôles distincts.
9. **Envoyer un webhook sortant.** Dans **Developer credentials**, un opérateur de l’organisation avec MFA configure le webhook, indique une URL HTTPS sur un hôte exact autorisé, fournit un secret de signature d’au moins 32 octets et active le point de terminaison. La mise à jour finale du crédit d’un client explicitement autorisé crée une livraison dans la file transactionnelle (outbox). L’événement HTTP `wallet.credit_posted` contient l’identifiant stable de l’événement, les identifiants client/dépôt, le montant, la devise, le solde disponible après les allocations et `settlement_status: unverified`. Il ne contient ni SMS brut, ni jeton de recherche client, ni référence fournisseur, ni secret de signature. La livraison signe le corps exact stocké avec HMAC-SHA256 sur `timestamp + "." + body` ; le récepteur reçoit `Webhook-Id`, `Webhook-Timestamp` et `Webhook-Signature: v1=<hex>`. L’identifiant et le corps restent stables d’une tentative à l’autre ; les récepteurs dédupliquent par identifiant d’événement. Huit tentatives bornées utilisent des délais de 30, 60, 120, 240, 480, 960 et 1 920 secondes, puis la livraison passe à `dead_letter`. La commande `wallet-webhooks:recover-deliveries` récupère les travaux échus. Les destinations HTTPS sortantes doivent satisfaire l’autorisation exacte de l’hôte et les contrôles DNS/adresses publiques ; les redirections et les proxys sont refusés. **Pause webhook** suspend les envois ; un opérateur avec MFA peut relancer un élément éligible en échec définitif si le point de terminaison est activé.

## Proposer, approuver et publier un modèle de parseur

Avant de marquer un SMS natif comme traité, l'application conserve durablement sa requête analysée dans le journal de soumission chiffré. Ce journal est lié à l'identifiant d'installation et à l'URL du serveur ; le transport vérifie encore cette liaison avant l'envoi. Un nouvel appairage vers une autre installation ou un autre serveur conserve l'ancien journal pour examen sans y rejouer les requêtes. Les reçus acquittés conservent les premières preuves immuables afin qu'une capture en double ne les réécrive pas. Une nouvelle version ne peut pas antidater son approbation ; un ancien SMS brut en dehors de toute période de capture utilisable reste à examiner et son heure de réception ne doit jamais être modifiée pour le rendre admissible.

La page Operations **SMS payment patterns** propose le parcours manuel pris en charge. Choisissez **Propose parser template** et entrez un identifiant fournisseur, l'expéditeur SMS exact et un modèle littéral contenant chacun des champs `{amount}`, `{currency}`, `{reference}`, `{customer}` et `{occurred_at}` exactement une fois. Utilisez un modèle synthétique pour une démonstration contrôlée. Cette action crée une proposition limitée à l'organisation et en attente de vérification ; elle n'envoie aucun SMS, n'exécute aucun modèle et n'active aucun parseur. La page montre le modèle proposé et son statut, jamais de preuve SMS brute.

Choisissez **Approve proposal** et sélectionnez une proposition en attente. La page et le service d'approbation exigent une MFA vérifiée. L'approbation enregistre l'opérateur et l'heure, mais n'active pas l'analyse. Choisissez ensuite **Create signed mobile release**, sélectionnez la proposition approuvée et choisissez une expiration future en UTC. Le service attribue la version suivante pour cette organisation, ce fournisseur et cet expéditeur, puis signe le JSON plat canonique de schéma chaîne `"1"` avec l'autorité de signature de parseur déjà configurée. La version contient `schema_version`, `provider`, `sender`, `template`, `pattern_version`, `approved_at`, `expires_at` et une `signature` Ed25519. La section **Signed release exports** affiche le JSON canonique. Copiez-le dans la commande **Import signed parser** du téléphone. Celui-ci vérifie la signature avec la clé publique du parseur intégrée à cet APK. La clé d'appairage ne peut pas signer les versions de parseur, et le JSON importé ne peut pas fournir sa propre clé de confiance.

L'endpoint existant `GET /mobile/operator-sms/pattern-releases` liste au plus 100 versions non expirées de l'organisation de l'installation appairée et activée. Il exige l'authentification mobile existante, la capacité `mobile:sync:read`, le middleware d'activation et la limitation de débit API. Il renvoie `Cache-Control: no-store` avec `{releases:[{release_id, encoded_release}]}`. `release_id` est un UUID opaque de l'endpoint. Le `parser_release_id` des preuves du dépôt est le condensat SHA-256 du transcript signé canonique ; ces identifiants ne sont pas interchangeables. Dans le parcours manuel, le téléphone reçoit le JSON `encoded_release` copié depuis la page Operations. L'endpoint existe aussi comme liste de versions pour les clients appairés.

La graine de signature serveur est la configuration protégée existante `OPENPAY_OPERATOR_SMS_PATTERN_SIGNING_SECRET`. Fournissez lors de la compilation de l'APK l'épingle publique de parseur correspondante avec `OPENPAY_OPERATOR_PATTERN_SIGNING_PUBLIC_KEY`. Cette clé publique n'est pas secrète. Ne créez pas de nouvelle autorité, n'utilisez pas la clé d'appairage et ne placez jamais une graine de signature dans une commande, l'application ou une version. L'artefact CI utilise une autorité synthétique de test ; il n'accepte que les versions de test correspondantes dans un environnement jetable. N'utilisez jamais cette autorité de test pour un déploiement réel. Sans épingle ou avec une épingle incorrecte, l'importation échoue en mode fermé.

Seules les versions avec les cinq champs peuvent alimenter le parcours portefeuille. Les anciens modèles à trois champs ne fournissent ni l'identité client ni l'heure fournisseur et restent en lecture seule. Toute modification de modèle exige une nouvelle proposition, une approbation MFA et une nouvelle version signée. Consultez [la limite d'intégration des modèles opérateur](operator-pattern-integration.md) pour le transcript LP16 exact, la signification des identifiants et les limites de migration.

## Contrat du portefeuille et du récepteur webhook

Configurez la politique des hôtes sortants avec `OPENPAY_WEBHOOK_ALLOWED_HOSTS`, une liste JSON de noms d’hôtes exacts. La configuration du point de terminaison et son secret sont limités à l’organisation ; le secret est stocké chiffré. Générez et conservez le secret d’un récepteur jetable dans le gestionnaire de secrets existant de l’appelant. Ne l’inscrivez ni dans ce guide ni dans le code source. Le récepteur vérifie le HMAC horodaté sur les octets bruts exacts de la requête, contrôle une fenêtre de cinq minutes et n’enregistre qu’une fois l’identifiant d’événement avant d’accuser réception. Il doit être idempotent : une expiration de délai peut survenir après l’enregistrement de l’événement. `examples/webhook-receiver.php` illustre un consommateur PHP/SQLite idempotent pour les tests contrôlés ; le contrat aller-retour est couvert par `WalletWebhookReceiverIntegrationTest` lorsqu’il est présent dans le checkout. N’exposez pas le serveur de développement PHP au réseau.

Le solde transmis est le solde final actuellement disponible après application, par le dépôt, des allocations de demandes de paiement en attente. Le webhook signale une modification du grand livre du portefeuille ; `settlement_status` reste volontairement `unverified`. Il ne doit jamais être présenté comme une confirmation de règlement par un opérateur mobile.

Dans ce prototype, `available_minor` représente un solde comptable interne, pas un solde réglé ou remboursable. L'allocateur existant rend les crédits SMS disponibles et peut débiter automatiquement les demandes de paiement en attente ; `settlement_status: unverified` est une information descriptive, pas un blocage imposé. Cette démonstration exige donc une organisation jetable isolée, des SMS synthétiques et des demandes de paiement de test. Elle n'autorise aucun versement ni transaction réelle. Une utilisation en production exige une décision produit distincte, examinée, ainsi qu'une autorité de règlement ou un blocage des soldes provisoires avant dépense ; cette modification n'ajoute pas cette politique.

## Enregistrer les résultats de vérification

Pour une exécution de preuve reproductible qui ne conserve aucun journal de console, consultez [sms-to-wallet-acceptance.md](sms-to-wallet-acceptance.md) et lancez :

```bash
export OPENPAY_OPERATOR_PATTERN_SIGNING_PUBLIC_KEY='iojj3XQJ8ZX9UtstPLpdcspnCb8dlBIb83SIAbQPb1w'
bash scripts/demo/sms-to-wallet-evidence.sh
```

Le script enregistre l'épingle publique du parseur, le commit, les heures UTC, l'état du dépôt, les codes de sortie et l'empreinte/taille de l'APK CI. Il ne conserve ni sortie console, ni configuration privée, ni autres variables d'environnement, ni identifiants ou secrets. Utilisez l'épingle publique synthétique CI de PR225 uniquement avec le signataire correspondant dans un environnement jetable ; pour un autre environnement de test, fournissez l'épingle correspondant au signataire déjà configuré. N'utilisez jamais le fixture en production.

Les tests automatisés ne prouvent ni le règlement par l’opérateur, ni l’authenticité d’un vrai SMS fournisseur, ni la durabilité matérielle après perte d’alimentation sur tous les appareils Android, ni la capacité en production, ni la préparation à manipuler de vraies données ou de vrais paiements. Un essai sur appareil complète les tests logiciels ; il ne les remplace pas.
