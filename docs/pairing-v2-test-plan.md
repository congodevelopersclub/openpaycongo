# Pairing v2 interoperability plan

`pairing-v2.fixture.json` is public deterministic test data. It contains test-only private seeds and a test-only QR secret. Production code must generate all seeds, secrets, and nonces with its CSPRNG and must never log or ship fixture values.

## Required tests

1. PHP uses ext-sodium `sodium_crypto_kx_seed_keypair`, `sodium_crypto_kx_client_session_keys`, and `sodium_crypto_kx_server_session_keys`. It must prove client send equals server receive and client receive equals server send for fixture keys.
2. Android native code uses maintained libsodium `crypto_kx_client_session_keys`; its host vector test proves client-send equals server-receive and client-receive equals server-send without raw X25519 or a custom KDF. Flutter test adapters may use the maintained Sodium binding only as test references.
3. Both runtimes construct completion AAD as length-prefixed bytes: protocol label, raw 16-byte intent id, raw 32-byte client public key. Both decrypt fixture completion ciphertext to exactly the 32-byte QR secret; change any AAD field, nonce, ciphertext, or key -> decrypt failure.
4. Both runtimes construct response AAD as length-prefixed bytes: response protocol label, raw 16-byte intent id. Both decrypt fixture response ciphertext to exactly the JSON shown; change any AAD field, nonce, ciphertext, or key -> decrypt failure.
5. Both runtimes validate and verify every QR field: strict JSON shape, canonical endpoint, expiry, suite, fingerprint, Ed25519 signature transcript, `pairing_secret`, and trust mode. Mutate each signed field once; every mutation must fail signature verification.
6. Server feature test issues fresh QR data, completes once with fresh client material, verifies encrypted response and `private, no-store`, then retries exact saved bytes and proves same encrypted `201` response without second pairing. Malformed, expired, unknown, altered, exhausted, or non-identical consumed attempts produce indistinguishable unavailable response. Invalid proofs consume the three-attempt per-intent budget under the row lock; expiry drains 100-row transactions until no due intent remains. The native limiter uses a shared cache lock to serialize check-and-consume: an 11-worker PostgreSQL concurrency harness proves at most ten admissions and correct stored count. A protector, database, random-source, lock-admission, or uncertain-commit failure returns generic no-store `503`, preserving the exact retry path. Do not assert secret values in logs/errors.
7. Mobile BLoC test keeps QR, secret, private key, directional keys, nonce, ciphertext, and SAS out of state `toString`, analytics, notifications, screenshots, backups, and crash reporting. The native bridge test proves directional keys do not enter Dart or a MethodChannel result; native code keeps them only in a pending process-scoped exchange until authenticated response decryption persists them in the Keystore-backed vault. Crypto coverage simulates a libsodium key-generation failure and proves the one-time QR credential cannot be reused; its transferred secret is wiped by the same cleanup scope. A typed unknown-outcome failure retries the exact four request fields once only while the shared 15-second deadline remains; a known non-`201` rejection or second unknown result fails closed without a new exchange. Transport classifies the end-to-end deadline, connection/framing failure, 408/429/5xx, and malformed/truncated/oversized `201` response as unknown outcomes.
8. Android #211 native-envelope tests prove Laravel v1 AAD/vector compatibility, 24-byte nonce and 32-byte XChaCha key lengths, bounded payload, counter exhaustion, counter restart/write-failure behavior, and opaque MethodChannel result. Native pairing-vector tests prove directional-key agreement, completion-secret decryption, AAD tamper failure, and memory disposal. They must also prove foreground/unlock denial before native key use. They do not prove transport delivery or response handling, nor power-loss behavior on every Android filesystem.

## Follow-up boundary

Laravel now implements confirmation, activation delivery, and the server half of counter-bound active mobile envelopes. #211 implements Android native sealing only. HTTP delivery, encrypted response handling, acknowledgement, revocation, rotation, and recovery still need feature tests before implementation claims.

Pairing #211 resolves the directional-key custody boundary: all production directional-key agreement, response decryption, and Keystore persistence are native. Test-only Flutter reference crypto is not the production pairing path.
